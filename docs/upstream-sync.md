# Staying in sync with Payload's template

This repository is a fork of `templates/blank` from the Payload monorepo, with a
Postgres adapter, object storage, migrations and a production Docker build layered
on top. Payload keeps changing that template: dependency bumps, generated admin
files, new Next.js conventions. This is how those changes get in without hand
diffing.

## The model

A branch, `upstream`, holds a faithful snapshot of
[`templates/blank`](https://github.com/payloadcms/payload/tree/main/templates/blank)
at one Payload release, with nothing of ours in it. Each sync adds one commit to
it, so its history is a series of upstream releases.

`main` shares its root commit with that branch: the first commit here is the
pristine template at v3.88.0, and everything this fork does sits in commits on top
of it.

```text
upstream   v3.88.0 ─── v3.89.0 ─── v3.90.0
              |  \           \           \
main          +──── (this fork)   merge       merge
```

So the merge base is genuine rather than declared, and merging applies only what
changed upstream between two releases instead of treating every file as new.

`workspace:*` versions are rewritten to the release being synced, because inside
the monorepo the template does not carry real version numbers and the dependency
diff would otherwise say nothing.

## Syncing

```bash
scripts/sync-upstream.sh 3.89.0
git merge upstream
```

Resolve the conflicts, run the checks, commit.

Expect `package.json` to conflict on almost every sync. That is the file doing the
useful work: it is where you see which versions Payload moved to, against the
places this fork deliberately differs (`db-postgres` rather than `db-mongodb`,
`storage-s3` and `pg` added, `next` pinned to a patch of our own choosing).

After merging dependency changes:

```bash
pnpm install
pnpm generate:importmap
pnpm generate:types
pnpm build
pnpm payload migrate:create   # only if the upgrade changed the schema
```

## What to watch for

- **Files this fork deleted.** The upstream template ships `tests/`, `.vscode/`,
  `playwright.config.ts` and `vitest.config.mts`, which are not here. If upstream
  changes one, the merge reports it as "deleted by us". Keeping it deleted is
  almost always right.
- **Files upstream adds.** New collections have appeared in the blank template
  before (`Folders.ts`, `Tags.ts`). They arrive silently, because nothing here
  conflicts with them. Read the merge diff and delete what does not belong in a
  minimal template.
- **`src/app/(payload)/`** is generated by Payload and should track upstream
  closely. Take their side unless you know why not.
- **`src/collections/Media.ts`** has a local `staticDir`, and
  **`src/payload.config.ts`** is substantially ours. Expect to resolve these by
  hand rather than taking either side wholesale.

## If the upstream branch is lost

It is recoverable from `main`, because `main`'s root commit is the snapshot:

```bash
git branch upstream "$(git rev-list --max-parents=0 main)"
```

Then sync it forward to whichever release it was on. Do not rebuild it by running
the sync script from scratch: the tree would be identical but the commit would not
(a commit hashes its timestamp too), so the new branch would share no history with
`main` and every merge would come back as one giant unrelated-history conflict.

If that has already happened, declare the baseline instead of pretending:

```bash
scripts/sync-upstream.sh <the version this fork currently matches>
git merge -s ours --allow-unrelated-histories upstream \
  -m "Record the upstream template baseline"
```

`-s ours` records the parent without changing a single file, which is what makes
later merges compute the right diff. Getting the version wrong poisons every sync
afterwards, so it must be the release this tree actually came from.
