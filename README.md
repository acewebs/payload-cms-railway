# Payload CMS 3 on Railway

**Payload CMS + PostgreSQL + Railway Bucket, fully configured for production.**

A Payload CMS 3 starter you can deploy to Railway in one click and then build on.
PostgreSQL, persistent object storage, database migrations, a healthcheck and a
production Docker build are already wired together, so there is nothing to
configure between clicking deploy and creating your first admin user.

This is deliberately not a website starter. There are no pages, posts, forms or
demo content to delete: just `users` and `media`, and room for your own schema.

Payload runs inside Next.js, so hosting it takes more than starting a container.
Uploaded files need durable storage outside the container, schema changes need
controlled migrations, and the pieces need to be connected to each other. Those
are the parts this template owns, and they are the parts a self-hosted Payload
usually gets wrong: a container filesystem is ephemeral, so uploads written to
disk vanish on the next deploy, and pushing schema changes straight to a live
database is fine in development and dangerous in production.

Published on the Railway marketplace as
[Payload CMS 3 Production Ready](https://railway.com/deploy/payload-cms-3-production-ready).
The listing copy is mirrored in [docs/marketplace-listing.md](docs/marketplace-listing.md).

|                         |                                                                               |

| PostgreSQL              | Provisioned by the template, connected over Railway's private network         |
| Railway Storage Bucket  | S3-compatible object storage, provisioned by the template                     |
| Persistent uploads      | Media goes to the bucket, so it survives every redeploy and restart           |

| Generated secrets       | `PAYLOAD_SECRET` is generated by Railway at deploy time                       |

## Deploy to Railway

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/deploy/payload-cms-3-production-ready)

Railway creates three things: this application, a PostgreSQL database and a
storage bucket. Every variable the application needs is filled in from those two,
so **no configuration is required**. The first deploy builds the image, applies
the migrations in this repository and starts the server.

### Deploying this repository directly

The button above deploys a published Railway template. To deploy your own copy of
this repository instead, use the Railway CLI:

```bash
railway login
railway init
railway config apply          # application + database, variables wired
scripts/railway-bucket.sh ams # bucket + its five variables
railway domain
```

`.railway/railway.ts` describes the application and the database. The bucket is a
separate script because a bucket declared in that file currently reports success
without creating anything, which would leave uploads going to disk. Applying the
file owns the environment: anything not described in it is deleted, so point it at
a new project rather than one that already has other things in it.

If you would rather click through the dashboard, create the Postgres and bucket
services yourself and set the variables listed in
[docs/railway-template.md](docs/railway-template.md). Without at least
`DATABASE_URL` and `PAYLOAD_SECRET` the container exits during migration and the
deploy fails.

## First login

Open the deployment URL and add `/admin`:

```text
https://your-app.up.railway.app/admin
```

The first visit shows a "create first user" screen. That account is the first
Payload admin.

## Local development

```bash
git clone https://github.com/acewebs/payload-cms-railway.git
cd payload-cms-railway
cp .env.example .env
docker compose up -d postgres
pnpm install
pnpm dev
```

The app is on <http://localhost:3000>, the admin panel on
<http://localhost:3000/admin>.

`.env.example` already points `DATABASE_URL` at the compose database. Set
`PAYLOAD_SECRET` to anything; `openssl rand -hex 32` is a good source. If port
5432 is taken on your machine, set `POSTGRES_PORT` in `.env` and update
`DATABASE_URL` to match.

Uploads go to `./media` on disk locally, because no bucket is configured. See
[Media uploads](#media-uploads) if you want to exercise the production code path.

## Creating collections

Collections live in `src/collections` and are registered in
`src/payload.config.ts`:

```ts
collections: [Users, Media, YourCollection],
```

After changing a collection, regenerate the TypeScript types:

```bash
pnpm generate:types
```

In development the Postgres adapter pushes schema changes straight to your local
database, so you can iterate without writing migrations. Production never does
this. When you are happy with the shape, create a migration (below).

## Database migrations

Development uses Drizzle's push mode. **Production only ever runs committed
migration files.** That is the difference between a starter and something you can
put real content in.

Create a migration after changing your collections:

```bash
pnpm migrate:create   # writes src/migrations/<timestamp>_<name>.ts
```

Commit the generated files. On the next deploy they are applied automatically,
before the new version starts serving traffic:

```text
build  ->  run migrations  ->  start application  ->  healthcheck  ->  traffic
```

If a migration fails, the container exits, the healthcheck never passes and
Railway keeps the previous version live. You get a failed deploy instead of a
running application pointed at a schema it does not understand.

Other commands:

```bash
pnpm migrate          # apply pending migrations
pnpm migrate:status   # show which migrations have run
```

On a deploy the container runs `pnpm migrate:deploy`, which wraps the CLI in
`scripts/migrate.mjs`. It waits for Postgres to accept connections (on a cold
deploy the database may still be booting) and takes a Postgres advisory lock
first, so scaling to several replicas cannot run the same migration twice. It
also refuses to run against a database whose schema was created by development
push, because `payload migrate` asks for confirmation in that case and a
container has no way to answer. Set `RUN_MIGRATIONS=false` on the service if you
would rather run them yourself.

## Media uploads

|                   |                                                                   |
| ----------------- | ----------------------------------------------------------------- |
| Railway           | Uploads go to the Railway Storage Bucket                          |
| Local, by default | Uploads go to `./media` on disk                                   |
| Local, optional   | Uploads go to MinIO, which is the same S3 code path as production |

The switch is automatic: the S3 adapter is enabled when `S3_BUCKET`,
`S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` are all set, and Payload falls back
to disk when none of the `S3_` variables are set. Nothing production-specific runs
locally by accident.

Setting only some of them is refused at startup rather than quietly falling back.
A half-configured bucket is the one case that loses data: uploads appear to work,
then disappear with the container filesystem on the next deploy.

Railway buckets are private and cannot be made public, so files are streamed
through Payload at `/api/media/file/<filename>` rather than linked directly at
the bucket. Access is controlled by the `read` access function on the `media`
collection, which this template leaves open to everyone.

To run the S3 path locally:

```bash
docker compose --profile s3 up -d
```

then uncomment the `S3_*` block in `.env`. MinIO needs
`S3_FORCE_PATH_STYLE=true`; Railway buckets do not.

## Updating Payload

Every `payload` and `@payloadcms/*` package must sit on exactly the same version.
Update them together:

```bash
pnpm up "payload@latest" "@payloadcms/*@latest"
pnpm install
pnpm generate:importmap
pnpm generate:types
pnpm build
```

Then check whether the upgrade changed the database schema:

```bash
pnpm migrate:create
```

If it produces a migration, commit it with the dependency bump so the two land in
the same deploy. If it produces nothing, the upgrade needs no schema change.

Read the [Payload release notes](https://github.com/payloadcms/payload/releases)
before a major version bump. Next.js is pinned to a version Payload supports; do
not upgrade it independently of Payload.

Payload also changes the template this repository forked from, including the
generated admin files under `src/app/(payload)/`. Those changes come in through
the `upstream` branch rather than by hand:

```bash
scripts/sync-upstream.sh 3.89.0
git merge upstream
```

See [docs/upstream-sync.md](docs/upstream-sync.md) for how that works and what
usually conflicts.

## Railway architecture

```text
                    +---------------------+
                    |     Payload CMS     |
                    |   Next.js + Payload |
                    +----------+----------+
                               |
                +--------------+--------------+
                |                             |
                v                             v
          PostgreSQL                   Railway Bucket
       (private network)                (S3-compatible)
```

PostgreSQL is reached over Railway's private network. Buckets are only reachable
over public networking, which is a Railway platform limitation rather than a
choice in this template.

## Environment variables

Railway sets all of these for you. They matter for local development, and if you
ever move the app somewhere else.

| Variable                 | Required   | Notes                                                            |
| ------------------------ | ---------- | ---------------------------------------------------------------- |
| `DATABASE_URL`           | yes        | Postgres connection string                                       |
| `PAYLOAD_SECRET`         | yes        | Signs tokens and cookies. Changing it logs everyone out          |
| `S3_BUCKET`              | production | Bucket name. Enables S3 storage when set with the two keys below |
| `S3_ACCESS_KEY_ID`       | production |                                                                  |
| `S3_SECRET_ACCESS_KEY`   | production |                                                                  |
| `S3_ENDPOINT`            | production | `https://storage.railway.app` for Railway buckets                |
| `S3_REGION`              | no         | Defaults to `auto`                                               |
| `S3_FORCE_PATH_STYLE`    | no         | `true` only for MinIO and older buckets                          |
| `NEXT_PUBLIC_SERVER_URL` | no         | Leave unset unless you need Payload to emit absolute URLs        |
| `RUN_MIGRATIONS`         | no         | Set to `false` to skip migrations at container start             |
| `PORT`                   | no         | Set by Railway                                                   |

`NEXT_PUBLIC_SERVER_URL` is intentionally unset by default. Payload then uses
relative URLs, which means the admin panel works on the Railway-generated domain
and on any custom domain you add later, with no redeploy and no CORS
configuration. The CORS and CSRF allowlists are still built at runtime from
`RAILWAY_PUBLIC_DOMAIN`. If you run the service with no public domain at all, set
`NEXT_PUBLIC_SERVER_URL`: with neither variable there is no known origin, and
Payload treats an empty CSRF allowlist as nothing to enforce.

## Repository layout

```text
src/
  app/
    (frontend)/        the placeholder landing page, yours to replace or delete
    (payload)/         generated Payload routes, do not edit by hand
    api/health/        the Railway healthcheck
  collections/         Users and Media
  migrations/          committed, applied on deploy
  payload.config.ts    the whole Payload configuration
scripts/migrate.mjs    wait for Postgres, lock, migrate
docker/entrypoint.sh   migrate, then start the server
Dockerfile             multi-stage production build
.railway/railway.ts    the app and database as Railway infrastructure-as-code
scripts/railway-bucket.sh  creates the bucket and wires its credentials
```

Publishing your own copy of this template? See
[docs/railway-template.md](docs/railway-template.md) for the exact service
settings and variable references.
